# 音频起播音量兼容修复

## 分支与范围

两个仓库均使用 `codex/sound-volume-compatible` 分支，目标均为各自的 `master`。

- hxmaker 基线：`82badeed15dd6d662126feaa6ad88306d35ad977`。
- hxmaker-openfl 基线：`dfd51fed0b062405753de48edfa2579de114d490`。
- 本次仅包含音频修复，不合入旧 PR 中的布局、Graphics、ASTC 等无关改动。
- `ISound`、`ISoundChannel`、`IEngine` 和 `IRender` 均不修改，也不新增后端接口。
- 不修改 OpenFL、Lime 或全局 haxelib 配置。

## 问题与实现

原流程是 `SoundManager` 先调用 `root.play()`，再调用返回声道的 `setVolume()`。底层播放已经开始，初始音量未必等于管理器设置。循环时创建新的底层声道，也会丢失上次设置。

资源类 `hx.assets.Sound` 新增可重写的 `play(isLoop, volume, pan)`。默认实现仍调用原 `ISound.play(isLoop)`，再设置声道音量，因此其他后端不必修改即可编译使用。

hxmaker-openfl 的 `SoundRequest` 创建 `OpenFLSoundAsset` 资源。该类重写资源播放方法，调用具体后端的 `playWithTransform()`。标准 OpenFL 路径使用已有的 `Sound.play(0, 0, transform)`，在起播前传入本次音量和声像。

调用链如下：

```text
SoundManager.playEffectSound / playBGMSound
  → Sound.play(isLoop, volume, pan)
  → OpenFLSoundAsset.play
  → OpenFLSound.playWithTransform
  → OpenFLSoundChannel
  → openfl.media.Sound.play(0, 0, transform)
```

每个逻辑声道保留自己的 `SoundTransform`，首次播放与循环重播共用入口。不同声道之间不共享音量，不把暂存音量写回声音资源，不使用反射、全局临时变量或延迟起播。

循环时不再调用全局 `SoundManager.updateVolume()` 扫描所有声道，当前声道直接使用自己缓存的音量。`setVolume()` 更新缓存，下一轮继续使用最新值。

## 声道生命周期

- 保留循环声道每轮发送 `SOUND_COMPLETE` 的行为，业务监听无需迁移。
- 管理器仅在非循环声道完成时移除跟踪；循环的单轮完成不再导致失去调音和停止能力。
- 新增 `SoundEvent.SOUND_STOP`，由 OpenFL 适配层在主动停止或重播失败时发送。
- 停止前解除底层完成监听，并标记为已停止，防止停止过程中的回调重新启动循环。
- 管理器收到停止事件时解除自己的监听并移除音效或 BGM 引用。
- 统一停止时先换出跟踪数组，避免停止事件删除数组元素而漏停后续声道。
- 起播失败时，新的资源播放入口返回 `null`，不把空声道加入管理器。旧的 `root.play(isLoop)` 仍保留原来的返回方式。
- 重播失败仍发送本轮完成事件，然后发送停止事件，清理循环声道的管理器引用。

这些是本次有意修正的行为：循环音效在首轮结束后仍受全局设置控制；主动停止后及时释放跟踪；BGM 失败或停止后不再返回已失效的缓存声道。

## 兼容边界与合入顺序

1. 先合入或同时使用 hxmaker 分支，再合入 hxmaker-openfl 分支。新的后端依赖 `Sound.play()` 和 `SOUND_STOP`。
2. 新 hxmaker 搭配旧后端可保留原播放路径，但旧后端没有起播修复，也不发送停止事件，不能视为完整修复。
3. 标准资源加载链 `Assets → SoundFuture → SoundRequest` 会自动创建适配资源。手动构造资源时，应使用 `hx.core.OpenFLSound.OpenFLSoundAsset`；手工 `new Sound()` 再设置 `root` 仍走默认兼容路径。
4. `OpenFLSoundAsset.root` 若被替换为其他 `ISound` 实现，会回到默认兼容路径。直接调用 `root.play()` 不带资源层的音量参数，保持原调用语义。
5. `hxmaker_sound` 与 `wechat_zygame_dom` 的底层播放参数和实现不同，本次保持原起播方式，并在每次起播后立即应用缓存音量，修复循环时丢失设置的问题；这两个分支不承诺消除起播瞬间的音量窗口。彻底修复它们需要单独适配各自的播放实现。
6. 其他后端若要及时清理主动停止的循环声道，可通过现有事件接口发送 `SOUND_STOP`，不必修改 `ISoundChannel`。未发送该事件的实现只能在管理器统一停止时清空跟踪。
7. 本次不改动底层 Howler 队列；不能据此保证所有版本和宿主下的播放中调音行为。原 PR 关于队列永久丢弃音量的具体根因仍需实际复现确认。
