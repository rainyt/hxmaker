# 纯二维上下文恢复诊断

这是静态的纯二维页面，不创建 Scene3D，也没有动画或强制重绘心跳。Canvas 外的 HTML 控件负责触发丢失、记录人工结果和导出报告；即使二维画面消失，也能继续操作。

**用户已确认修补后测试正确。** Safari 报告记录了 4 轮恢复、1 次手动字形图集重建及最终人工通过；11 个文字全部准备完成，pending/stale 均为 0，详见 [实测记录](Baselines/README.md)。首轮文字消失的失败报告也保留供对照。助手本轮只分析报告并更新记录，没有执行测试。

如需复测，由用户在本目录运行：

```bash
arch -x86_64 lime test html5
```

需要同时使用本轮更新后的 hxmaker-openfl 和本地 OpenFL。此次 OpenFL 修复位于 `/Users/rainy/Documents/haxelib-self/openfl`；只更新 hxmaker 仓库或更换回未修复的 OpenFL，不能覆盖 Shader 与 Graphics 缓冲重建的问题。

## 人工操作

1. 加载后确认静态文字、普通图片、最近点/线性过滤、自定义 Shader 色调、嵌套裁剪、模糊滤镜和右侧 MakerDisplay 位图缓存均正常。
2. 静置数秒，再点击“丢失并恢复”。一秒后请求浏览器恢复，等待画面重新出现。
3. 页面没有重新构建业务对象，也没有重载 Assets。确认各项恢复后，点击“记录画面通过”；异常时点击“记录画面异常”。
4. 重复至少三轮，检查中文和图案不会逐轮消失，色调与裁剪不变，且无需改变文字或窗口尺寸才能恢复。
5. 点击“导出记录”。报告保存请求次数、浏览器恢复事件数、后端设备代次、完成恢复次数、人工记录与错误。没有完成后端恢复时不能记录通过；这些计数不能替代人工画面确认。

若文字仍缺失，先导出一次报告，再点“重建文字图集”，观察变化后再次导出。该按钮用于定位，不应成为正常恢复必须手动操作的步骤。

新版报告 `version=2` 包含 `text` 和 `textSnapshots`：记录驻留文字数量、待预写数量、已准备/过期数量、图集与字形数量、写入计数和 `cpuPixels`。丢失前、恢复事件后及人工记录时分别留存 CPU 诊断信息，不执行 GPU 像素读回。恢复后预期 `cpuPixels=true`，文字完成预写后 pending/stale 降至 0；非零字形计数只说明逻辑已登记，不证明像素可见。

正常加载保留原 GPU 图集路径。HTML5 首次恢复时重新生成保留 CPU 像素的图集，以后恢复可重新上传；强制重建会再次生成字形。CPU 像素有额外内存成本，2048×2048 RGBA 每张约 16MiB，浏览器实际开销可能更高。

恢复请求不支持或超时时会显示提示。后台等待可能导致计时器延后，测试时保持前台。此诊断只覆盖引擎可重绘的资源；业务创建并丢弃了全部来源的一次性 GPU 图片仍需要业务自行提供重建方式。

纯二维确认后，再使用 [混合验收场景](../engine-acceptance/README.md) 检查角色、阴影、双视口与二维覆盖层。先分别完成默认 GL 状态保护、`-D hxmaker_3d_no_vao` 的回退路径检查，再导出结果。
