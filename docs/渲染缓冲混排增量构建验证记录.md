> 1.2.0 集成入口与最新验证见《1.2.0渲染优化同步记录.md》。本文中的开发分支及未提交状态描述对应历史阶段。

日期：2026-11-11。跟踪提议：https://github.com/rainyt/hxmaker-openfl/issues/11 。

## 阶段 D 的含义与本轮范围

阶段 D 是依据实际收益扩大缓存覆盖范围，不要求一次缓存所有 Graphics 和特殊作用域。

第一期后端已进入提交 `eb50821`。本轮继续在两个仓库的 `codex/incremental-render-buffer-20261111` 工作分支上处理 Graphics 与图片/字形混排；本轮改动未提交或推送。

常见例子是一个背景 Quad 后面跟随多个 Image/Label。第一期一旦遇到 Graphics，就使整个批次回退，后方图片无法使用缓存。本轮保留 Graphics 原来的全量构建，同时允许同批图片和字形复用未变化的缓冲片段。

遮罩、滤镜、自定义 shader、离屏与 cacheAsBitmap 的保守回退规则保持第一期策略。本轮没有实现 Graphics 网格自身的增量缓存。

## 实现与正确性规则

主要修改 hxmaker-openfl 的 `src/hx/render/ImageBufferData.hx`，新增 `src/hx/render/ImageBufferOffsets.hx`。普通图片的 ImageBufferEntry 字段结构与第一期提交一致。

- Graphics 沿用原来的切批、纹理登记、顶点、UV、索引和颜色写入；实际接受一条三角形命令后，将对应的旧图片记录和偏移记录清空。
- 混排图片除了对象身份和属性快照，还校验坐标、索引、逐顶点属性三种实际起点。前面网格变长或变短，即使命令序号未变，也会失效重写。
- 额外偏移存在批次独立表内，仅混排片段按需分配，不给每个普通图片记录增加三个字段。
- 从未分配偏移快照的普通图片片段，以固定四边形的命令槽位推导起点。首次进入混排时，只在推导位置与实际位置一致时复用。
- 每次图片片段全量重写时都会更新已有偏移记录，包括混排中断后切回纯图片的情况；不允许元数据对应旧布局而缓冲已经被新布局覆盖。
- Graphics 始终从当前游标单调追加，写入不超过下一个游标。图片的三类起点匹配旧记录，才能证明它的片段未被前方网格覆盖。
- 尾部缩短与退出特殊作用域时同步清理偏移表；纯 Graphics 不保留空图片记录尾部。额外偏移对象只保存整数，不持有显示对象或纹理。

## 退化控制

初版混排实现在持续变长网格场景比全量慢约 8%，因此没有直接交付该版本。

当前统计连续布局失配影响的图片比例：连续两次已具备缓存的构建中，至少半数图片失配，则退让 60 次构建。单次布局调整直接重新采集，不因一次插入或改尺寸就立即进入长期退让。

退让期采样首张图片的属性及位置变化，稳定后重新采集。探测是性能启发式，不是正确性依据；遇到不能复用的片段始终完整写入。首项未必代表整个批次，部分动态模式仍会发生周期性重新采集。

还区分了属性变化与结构失配：强制重写全部属性，不等同于这些属性本身持续变化，避免稳定批次被误判为低收益动态批次。

本批已确定全量回退后，避免每张图片重复检查完整渲染作用域；所有纹理登记和切批判断仍照常执行。

## 正确性验证

用户已授权测试。本轮最终全量对照通过 **588311 次检查**。在第一期覆盖之外，新增：

- 首部、中部和重复 Graphics 混排；网格全量写入后，同批图片仍可命中。
- 顶点数量变化而索引数量不变，以及索引数量变化而顶点数量不变。
- 网格只改变数值、缩短、增减绘制命令；同一图片跨网格重复出现。
- 相同拓扑的网格替换图片后，前后缓存片段仍正确。
- 同一个 Graphics 跨纹理上限分批并恢复命令游标，改变纹理上限后的批次边界。
- 180 帧确定性混排布局变更，动态网格退让与稳定恢复。
- 纯图形清空图片记录，混排构建中断后先切回纯图片，再次进入混排。

真实 Chrome/OpenFL WebGL 连续 **96 帧逐像素一致**，确认实际非空绘制和 **732 次槽位复用**。新增背景 Quad、抗锯齿路径、网格命令数变化和九宫格；仍覆盖文字、嵌套遮罩、滤镜输出、shader 与 cacheAsBitmap。特殊作用域的像素验证用于确认回退正确，不代表这些作用域已经启用缓存。

浏览器使用 SwiftShader 软件 WebGL；没有据此推断移动设备 GPU 性能。开发构建通过，既有输入框溢出 94 项和右键菜单 97 项断言通过。

## CPU 基准

macOS arm64、Haxe 4.3.7、Node 22.14.0。每场景 4000 项，预热 100 帧后采样 350 帧，交替两种路径的计时顺序，关闭诊断计数，独立三轮。表中取三轮各统计量的中位数，单位 ms。

只计 CPU 缓冲构建，不包含场景更新、OpenFL 提交或 GPU 上传。下面的收益不是整帧加速比例。

| 混排场景 | 全量中位数 | 增量中位数 | 全量 P95 | 增量 P95 |
| --- | ---: | ---: | ---: | ---: |
| 首部网格 | 0.2245 | 0.1388 | 0.3111 | 0.2152 |
| 中间网格 | 0.2340 | 0.1464 | 0.3386 | 0.2391 |
| 每100图片一个网格 | 0.2382 | 0.1500 | 0.3030 | 0.2115 |
| 持续变长网格 | 0.2356 | 0.2300 | 0.2981 | 0.2892 |
| 纯Graphics | 1.0087 | 1.0141 | 1.1727 | 1.1516 |

稳定混排场景的配对中位构建耗时显著下降；持续变长网格与纯 Graphics 主要保持全量路径，额外检查仍有成本。

### 与第一期的纯图片对照

第一期基线从提交 eb50821 提取 ImageBufferData 与 ImageBufferEntry 到临时 class-path 编译，没有切换或修改工作分支。每轮先运行第一期，再运行当前版本。不同进程与 CPU 频率存在波动，因此同时保留各自全量路径与 P95 数据，不能把跨进程差值全部归因于算法。

| 纯图片场景 | 第一期增量中位数 | 当前增量中位数 | 第一期增量 P95 | 当前增量 P95 |
| --- | ---: | ---: | ---: | ---: |
| 静止多数 | 0.1312 | 0.1339 | 0.1988 | 0.2009 |
| 全部移动 | 0.1656 | 0.1654 | 0.2340 | 0.2278 |
| 持续换序 | 0.2387 | 0.2309 | 0.3264 | 0.3285 |
| 矩阵、UV与透明度同时变化 | 0.1918 | 0.1991 | 0.3156 | 0.3071 |
| 完整颜色静止 | 0.1739 | 0.1764 | 0.3177 | 0.4199 |
| 完整颜色全动态 | 0.5797 | 0.6086 | 0.8779 | 0.8403 |

新增混排安全判断并非零成本。当前样本中，纯图片的静止与移动中位数接近第一期；矩阵、UV和透明度同时变化的微基准存在小幅额外开销；颜色场景的跨进程耗时与 P95 波动较大。没有宣称所有纯图片场景都比第一期更快，实际项目仍应比较整帧 CPU 与 P95。

```bash
/usr/local/bin/haxe test/incremental-buffer.hxml -D hxmaker_buffer_stats
node --require ./test/context-menu-preload.js bin/incremental-buffer-check.js

/usr/local/bin/haxe test/incremental-buffer.hxml -D buffer_mixed_benchmark
node --require ./test/context-menu-preload.js bin/incremental-buffer-check.js

/usr/local/bin/haxe test/incremental-buffer.hxml -D buffer_benchmark
node --require ./test/context-menu-preload.js bin/incremental-buffer-check.js

/usr/local/bin/haxe test/incremental-buffer-browser.hxml
node test/run-incremental-buffer-browser.cjs
```

浏览器脚本需 Playwright，可用 HXMAKER_PLAYWRIGHT_MODULE 指向项目外安装的模块，用 HXMAKER_CHROME 指定 Chrome。本机 Haxe manager 包装器标准库路径未配置，因此使用 /usr/local/bin/haxe。没有新增项目依赖。

## 后续选择

建议下一步单独评估遮罩中的普通 Image/Label，直接针对 Scroll/ListView 的覆盖范围。任意 Graphics 网格自身的缓存、滤镜与离屏缓存需要独立处理。Spine 的实际动画、小游戏真机、原生目标和精确内存占用仍未单独验证。
