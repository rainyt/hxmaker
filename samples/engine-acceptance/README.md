# 3D 引擎验收与性能基线示例

这是独立的验收台，使用固定资源与负载记录性能、采样状态和资源生命周期。启动后仅显示场景，不自动运行性能套件、资源循环或上下文恢复诊断。

**交付状态：代码与资产已准备，尚未编译、启动或执行验收。本目录目前没有实测基线。** 之前的贴图角色示例已由用户反馈正常，不能把该结果作为本示例通过的证据。

## 启动

需要同时使用本轮更新后的 hxmaker 与 hxmaker-openfl。在本目录由用户执行：

```bash
arch -x86_64 lime test html5
```

正式建立基线时，为源码版本加一个易辨认的标签：

```bash
arch -x86_64 lime test html5 -D hxmaker_baseline_label=before-optimization
```

标签会写入报告；应自行记录对应提交、未提交修改和设备型号。依赖版本号取自实际构建定义，开发版库的版本号不能代替提交标记。

不要叠加 `hxmaker_3d_profile`、`hxmaker_3d_regression` 或浏览器性能录制来建立此处的普通基线，额外探针与日志会改变测量成本。

## 建议操作顺序

1. 用“下一个场景”浏览各场景，检查模型、UV、动画、深度、二维文字和遮罩。分别点击“记录画面通过”或“记录画面异常”，它们只保存当前场景的人工记录。
2. 点击“采样当前”记录单个负载；或者点击“运行完整套件”，依次采集下表 14 个固定场景。保持页面前台、窗口大小与浏览器缩放不变。
3. 性能采样结束后再点击“采样状态诊断”，检查两张二维贴图与嵌套遮罩，并观察一致次数、异常项。此模式包含同步 GL 查询，不纳入性能基线。
4. 点击“资源循环 ×20”，观察加载、绘制、释放和延迟回收结果。结束后会恢复普通资源池与预览。
5. 单独点击“上下文恢复诊断”，恢复后检查角色、二维贴图、文字和遮罩；记录人工结果。已有工具链曾出现二维恢复失败，这个入口不预设成功。
6. 点击“导出 JSON”。HTML5 下载报告；原生目标使用文件保存入口。若在采样期间导出，会先结束本次采样并保留 `complete=false` 的部分结果，避免导出开销污染完整样本。

“停止”保留未完成的性能结果。资源循环若正在请求图片，会等待请求结束或超时后清理，不把仍在加载中的资源当成已释放。

## 固定负载

| 场景 | 内容 | 主要观察项 |
| --- | --- | --- |
| empty | 空 Scene3D | 状态保护、离屏目标与最终合成的固定开销 |
| boxes-multi | 256 个方块、20 张贴图、多纹理 | 超过常见纹理槽位数时的自动拆批 |
| boxes-single | 相同方块与贴图、单纹理 | 与多纹理模式比较画面和批次 |
| actors-10 | 10 个低模动画角色 | 基础角色负载 |
| actors-30-multi | 30 个低模动画角色、多纹理 | 实例数量与合批 |
| actors-30-single | 相同角色、单纹理 | 多纹理对照 |
| dense-1 | 1 个高密度全双权重角色 | 通用 CPU 蒙皮与上传 |
| dense-4 | 4 个高密度全双权重角色 | 49,152 个角色三角形，不含地面 |
| dense-shadow-1024 | 相同高密度角色、1024 阴影 | 阴影额外提交与估算附件占用 |
| dense-shadow-512 | 相同角色、512 阴影 | 分辨率与投影质量对照 |
| static-redraw | 30 个静止角色、每帧重绘 | 相同几何重复提交 |
| static-cached | 30 个静止角色、关闭 autoRender | 稳态应只合成，主场景批次和上传量应为零 |
| two-views | 主视口 10 个角色，次视口 2 个 | 独立目标、二维显示顺序与多场景状态恢复 |
| nested-mask | 10 个角色、嵌套 Scroll 遮罩、换贴图 | 父级裁剪、共享采样与失效通知 |

主视口逻辑尺寸固定为 900×420，次视口为 240×170。实际像素尺寸受设备像素比与后端尺寸上限影响，报告记录实际离屏尺寸。相机、网格排列、播放起点和每帧 1/60 秒模拟步长固定，不使用随机输入。

低模角色为 384 顶点、192 三角形，只有躯干使用双关节混合，其余网格可走刚性优化。高密度角色为 7,776 顶点、12,288 三角形，16 个网格全部使用双关节权重。两者共享相同骨架、动画和三张图片。高密度版本用于控制计算量，不模拟复杂 PBR 美术成本，也不能代表所有真实角色。

所有资源通过 Assets 加载。普通采样使用统一常驻资源池，避免场景切换时把网络与图片解码混入稳态帧耗时。“重载资源”可重新加载资源池；报告中的资源清单提供包内文件的声明 SHA-256，不进行运行时完整性校验。

## 耗时与计数口径

每个普通案例先丢弃 120 帧预热，再采集 240 个已完成渲染回调对应的更新样本。60 FPS 时约 6 秒一组；完整套件约 84 秒，实际会随设备性能变化。切换时销毁旧场景并创建新场景的同步耗时另存 `setupMs`，不计入预热后的 CPU 分位数。普通资源池加载耗时单独保存在 `poolLoads`，包含请求、结构解析和图片解码，不包含随后的 GPU 首次上传；是否命中缓存需结合记录的缓存状态判断。

| 指标 | 含义 |
| --- | --- |
| frameIntervalMs | 读取相邻完整渲染结果的 UPDATE 间隔，包含调度、整页工作与帧率限制，不是 GPU 耗时 |
| meanObservedFps | 样本数量除以这些间隔的总时间，不对逐帧 FPS 做算术平均 |
| animationCpuMs | 上一轮显式 Model3D.update 的 CPU 墙钟时间，包含姿态和蒙皮 |
| renderCpuMs | 完整三维回调 CPU 墙钟时间，包括查询等待、状态保护、绘制、合成与恢复；双视口求和 |
| shadowCpuMs / mainCpuMs | 阴影 pass，以及主场景清屏、剔除、合批和提交时间 |
| compositeCpuMs / stateCpuMs | 最终纹理合成，以及状态快照和恢复时间 |
| animationAndRenderCpuMs | 上述动画与三维回调的和，不是完整应用 CPU 耗时 |
| mainDrawCalls / shadowDrawCalls | 本次实际重绘产生的提交；静态复用时为零 |
| compositeDrawCalls | 三维结果合成次数，单视口通常为 1 |
| mainUploadedBytes / shadowUploadedBytes | 本次顶点与索引上传字节，不包含所有驱动内部操作 |
| visibleMeshes / culledMeshes | 最近一次主场景重绘的可见与剔除数量，静态复用时保留场景库存描述 |
| targetBytes / shadowMapBytes | 附件的格式估算，不包含所有纹理、缓冲、程序和驱动占用 |
| jsHeapBytes | 浏览器提供时读取 JS 堆；可能不可用，且包含记录器自身分配与未回收对象 |

每项输出样本数、均值、最小值、P50、P95、P99 和最大值。分位数采用最近秩；前台长帧不剔除。超过 33.3 ms 的帧单独计数。60 FPS、16.67 ms 帧预算和 P95 20.83 ms 容差仅作参考，不自动代表整个引擎通过。

采样通过新增的 `scene.profilingEnabled=true` 获取计时，普通业务场景默认关闭。`scene.stats.renderId` 每次完整成功回调递增，`redrawThisFrame` 表示是否重绘主场景。旧 `drawCalls` 等字段仍表示最近一次主场景重绘，示例在静态复用时按零计入本帧数据。

读取在下一次 UPDATE 开头进行，与上一轮动画时间配对。没有新的渲染结果时不重复采样；若出现无法配对的多次回调、离屏尺寸意外变化或长时间无结果，该组明确结束为未完成，不拿最后一次回调冒充整帧成本。这类情况首先表示当前采样方法不适用，需结合错误信息定位。

HTML5 页面切后台或改变窗口尺寸会丢弃当前未完成窗口、记录事件，并重新预热 120 帧；已有完整结果保留。比较报告应核对设备、软件版本、浏览器缩放、窗口、实际目标尺寸、阴影实际状态、可见三角形与采样条件。

为了使静态复用场景仍执行二维合成，右下角有一个固定的微小明暗心跳。所有案例都包含相同 UI 更新和记录器开销，不能与关闭这些逻辑的其他应用直接比较。

## 长跑

“长跑 5 分钟”对当前配置采集不少于 300 秒的有效窗口时间，首个窗口预热 120 帧，之后每 600 帧形成一组，窗口间预热 2 帧以避开结果排序与日志输出。后台暂停与预热不计入有效时长，实际用时会更长。

每个窗口独立报告分位数，不把多个窗口的 P95 平均成整段 P95。报告可观察帧耗时、上传量、缓存引用和 JS 堆的趋势；JS 堆上涨本身不能证明泄漏。用户可提前停止，最后一组会标记未完成。

## 资源生命周期验收

资源循环先销毁预览和角色，释放普通资源池，再交替加载低模与高密度 GLB。每轮创建两个实例并完成至少一次实际渲染，停留至少 250 ms 后销毁场景与资产，共 20 轮。

报告也检查普通资源池是否在进入循环前回到了其加载前的引用基线。每轮记录加载耗时、已加载与已释放状态下的缓存引用/条目/可用 JS 堆，并检查：

- 资产引用总数回到开始循环时的基线。
- 实例几何和材质已销毁且引用数为零，Scene3D 标记为已销毁。
- 延迟回收后，本次观察到的共享图片已经释放。

独立示例临时将 RequestQueue.RELEASE_DELAY 从原值调整为 0.5 秒，最终等待至少 0.8 秒、清理到期项，再恢复原值。不会调用强制清空缓存接口，也不会把缓存的正常延迟释放当成泄漏。记录完成后再恢复普通资源池，所以报告中的最终快照早于界面重新加载后的资源状态。

这组检查覆盖引用与生命周期协议，不证明浏览器已经 GC 或驱动已经立即释放显存；发生错误或取消的轮次不会伪装成完整通过。不要把这个缩短全局释放延迟的诊断流程嵌入正常业务。

## 采样状态与上下文恢复

“采样状态诊断”创建独立探针：在三维绘制前后读取同一贴图的真实 min/mag/wrap 参数，并检查后置二维贴图的实际过滤。诊断期间局部关闭 OpenFL 的自动放大平滑，后置探针和销毁时恢复原值。报告记录一致次数、NEAREST / LINEAR 实际覆盖次数及异常内容。建议至少覆盖 120 次且两种过滤均出现，仍需人工确认贴图与遮罩画面。

“上下文恢复诊断”仅在 HTML5 支持 WEBGL_lose_context 时可执行，主动丢失后 1 秒请求恢复，10 秒仍未收到恢复事件则记错误。收到恢复事件只代表浏览器事件到达，不代表二维与三维均恢复。

上下文丢失时会出现独立 HTML 记录栏，即使 Canvas 中的文字和贴图丢失，也能记录恢复后画面异常并导出报告。诊断会结束正在记录的性能样本；整个过程不进入普通基线。

## 结果与验收范围

导出 JSON 包含环境、构建标签、资源清单、性能分组、同环境对照、人工画面记录、采样探针、生命周期结果、上下文事件与运行错误。`complete=false` 的案例不能作为完整基线。运行完整性能套件也不等同于整体验收通过，报告不会自动给整个引擎下结论。

对目标项目，至少应确认：各固定负载画面正确、多纹理开关不改变画面、静态复用减少提交、二维遮罩与双视口正常、资源循环通过，以及目标设备可接受的 P95。上下文恢复、原生与小游戏平台需分别保留实际结果；未执行的平台不能填“通过”。

结果存放约定见 [Baselines](Baselines/README.md)。资源已随示例提供；需要重建时执行 `python3 SourceAssets/generate_assets.py`，仅依赖 Python 标准库和仓库中贴图角色的生成器。
