本文保留优化前的 Trace 分析。后续代码改动、同环境对比与验证结果见 [渲染优化记录](../../基础3D渲染优化记录-20261016.md)。

## 结论

当前示例稳定阶段接近 60 FPS，但渲染提交存在明显的同步状态查询开销。优化优先级应是减少 WebGL 查询与状态往返，而非先修改多纹理 Shader 或引入实例化。

在动画回调内部的时间加权采样中，`getTexParameter`、`getParameter` 与 `isBuffer` 合计占约 87.4%，平均分摊约 4.42 ms/回调。完整动画回调平均为 5.06 ms。

这说明首版为确保 OpenFL 状态恢复正确而采用的完整快照，已经成为当前小场景的主要固定开销。正确性协议仍需保留，但实现应减少从 WebGL 反向查询状态。

### 1. 纹理参数读取是最大热点

调用链：

```text
Renderer3D.render
  → drawScene
    → submit
      → RenderStateGuard3D.rememberTexture
        → getTexParameter
```

对应 `hxmaker-openfl/src/hx/render3d/openfl/RenderStateGuard3D.hx` 的 `rememberTexture()`。它为当前回调首次遇到的每张纹理读取 min filter、mag filter、wrap S、wrap T 四项设置。

当前基础示例最多使用 13 张不同纹理，因此该路径按源码可产生约 52 次纹理参数读取/重绘；这属于按源码与示例配置推导的调用次数，不是 Trace 的精确调用计数。

多纹理合批减少了 DrawCall，却没有减少需要保护的独立纹理数量，所以这项开销仍可能保留。单纯进一步压低批次数，无法解决该热点。

### 2. 每次进入 Scene3D 都重新查询上下文状态

主要调用链：

```text
Renderer3D.render
  → new RenderStateGuard3D
    → getParameter
```

Guard 构造函数读取程序、目标、视口、深度、混合、像素上传状态和每个槽位的纹理绑定。Renderer3D.render() 还会读取纹理槽位、属性数量、目标尺寸和视口上限。

设备能力是上下文生命周期内基本不变的数据，适合在初始化和恢复时读取；动态状态则应由后端适配层维护或从可靠的 OpenFL 状态缓存取得，避免每次入场都完整查询。

MDN 的 WebGL 最佳实践明确指出，`get*Parameter()` 可能引起命令刷新和跨进程往返，不应依赖浏览器一定会缓存这些查询，见 [避免阻塞 API 调用](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#avoid_blocking_api_calls_in_production)。这与本 Trace 的热点相符。

### 3. 每帧 isBuffer 检查成本明显

对应 `Renderer3D.render()` 开头的缓冲有效性检查。该调用用于辅助判断上下文恢复，但时间加权采样中平均占约 0.32 ms/回调。

后端已有 CONTEXT3D_CREATE 事件处理，应优先通过设备代次和明确的上下文事件让句柄失效。逐帧 isBuffer 可移到诊断路径，不能在未覆盖恢复协议的情况下直接删除唯一的失效检测。

### 4. 当前其他计算不是首要热点

drawScene、submit、顶点打包、TypedArray 构建和 bufferData 等叶节点自身时间，在这份记录中远低于上述查询。不能把 submit 的包含子函数时间全部解释为绘制提交成本，因为其中大部分位于 rememberTexture 的同步查询。

这也不证明 CPU 世界顶点合并在大型场景中仍足够快；这里只能说明当前小型示例的优化应先处理固定状态开销。

## 开头的长任务与 GC

记录开头有一个 72.846 ms 的主线程 RunTask，其中 CpuProfiler::StartProfiling 占 72.298 ms。5 条 STATE_DROPPED 记录全部出现在开始后的约 2～68 ms，与该启动阶段重叠；其中包含分支帧记录，不能简单据条数计算掉帧率。

因此，这个约 72 ms 的峰值主要属于采样器启动，不应当作引擎每隔一段时间就会出现的渲染卡顿。随后动画回调最大为 6.50 ms。

GC 方面：

- MinorGC 两次，顶层耗时合计 1.096 ms。
- MajorGC 一次，顶层耗时 2.527 ms。
- 上述三次事件合计 3.623 ms，不再叠加它们内部的 GC 阶段。
- JS 堆计数约在 8.71～22.82 MB 之间波动。

GC 当前不是首要瓶颈。2.69 秒的记录也不足以判断是否存在长期内存泄漏。

## GPU 信息的边界

按当前 renderer_pid 过滤的 GPUTask 共 21,830 条，累计事件时长约 123.62 ms。这些是 GPU 进程中的任务事件，不能直接解释成 GPU 核心忙碌时间，也不能据此计算 GPU 利用率。

本记录没有逐个绘制的 GPU timer 数据，不能判断片元 Shader、离屏填充或显存带宽的准确占比。当前有充分证据优先优化主线程的同步状态查询，但没有依据把它表述为已证实的硬件 GPU 算力瓶颈。

## 建议的优化顺序

| 优先级 | 改动方向 | 正确性要求 |
| --- | --- | --- |
| 第一批 | 改造 rememberTexture，减少逐帧 getTexParameter | 共享纹理仍可能被 2D 修改，不能把首次读到的参数永久当作当前值；需统一跟踪采样状态、使用可靠的 OpenFL 缓存，或隔离资源 |
| 第一批 | 设备能力在上下文初始化时缓存 | 上下文重建后重新查询，不能跨设备复用 |
| 第一批 | 用上下文事件和代次替代逐帧 isBuffer | 保留明确的恢复与失效协议，必要时保留诊断检查 |
| 第二批 | 为可控的 OpenFL 接入建立状态快路径 | 保留完整兼容路径；不能直接跳过程序、目标、遮罩等恢复 |
| 第二批 | 缓存 uniform 位置、活动 uniform 描述和类型 | 材质参数仍要每批正确更新/重置；程序重建后失效 |
| 第三批 | 减少临时数组和矩阵副本，复用批次缓冲 | 先验证前两批收益，再用扩大模型数量的场景决定是否需要实例化 |

设备能力、程序反射与状态恢复应按不同生命周期缓存。不能为了消除查询，把可变化的共享纹理状态误当作设备常量。

约 4.42 ms/回调是三类查询在本次录制中的栈时间归属，不是承诺可全部消除的性能收益。改造后仍需同场景、同分辨率、同浏览器重录比较 P50/P95 和视觉正确性；也不宜据当前 60 FPS 推算最大模型数量。

## 本次建议

保留现有多纹理合批方案，先优化 OpenFL 与三维渲染器交界处的状态管理。最先处理 rememberTexture，其次缓存能力信息并移除逐帧句柄探测，再建立受控状态恢复快路径。

预期方向是降低每个 Scene3D 的固定提交开销，提高多场景和移动设备上的余量。具体收益必须由后续对照 Trace 验证，本次未修改实现。
