# 二维上下文恢复修复说明

用户反馈：主动恢复后，三维可以显示，二维图片和文字消失。补充字形恢复修补后，用户确认测试正确；Safari 纯二维报告记录 4 轮恢复及最终人工通过，见 [通过记录](../samples/context-recovery/Baselines/README.md)。助手本轮只读取报告和更新文档，没有执行测试。

首轮用户测试未通过：Safari 报告显示恢复入口完成 1 次、没有脚本错误，但人工记录失败，用户反馈文字消失。后续补充以下文字绘制与离屏处理后，再由用户测试通过；失败及通过的原始数据均保留在实测目录。

通过报告中，11 个驻留文字全部准备完成，pending/stale 均为 0，图集为 1 张、108 个字形。首次恢复重新生成字形，后续恢复复用 CPU 像素；第 3 轮后另有一次手动图集重建，所以最终文字代次 5、设备代次 4。该结果验证本轮 Safari 纯二维示例，不替代混合场景及其他平台的实际记录。

## 已确认的源码缺口

- OpenFL 重建舞台渲染器后，旧 Shader 仍可持有原 Context3D 和 GPU 程序。三类 Shader 初始化入口原先仅检查上下文是否为空。
- ShaderBuffer 的参数缓冲长期复用，没有设备归属；Graphics 的顶点、索引和四边形缓冲同样可能沿用旧句柄。
- hxmaker 的字形图集会调用 disposeImage，不能假设恢复时仍有 CPU 像素可以直接上传。驻留文字内容不变时，也不会自动重新写字形。
- hxmaker Engine 缺少统一恢复入口；静止显示树及依赖重绘的滤镜、位图缓存可能没有失效。
- BitmapData.draw 的离屏 OpenGLRenderer 也会被长期缓存，原先只判断是否为空，恢复后可能继续使用旧 Context3D。GPU 目标清屏也需要解析新设备上的 TextureBase。

## 本轮实现

OpenFL 在 Shader 初始化时切换到有效 Context3D。设备变化只丢弃程序并刷新属性/uniform 位置，保留 ShaderData、参数值与输入引用，不通过重建业务 Shader 替换实例。Graphics 和 ShaderBuffer 按 Lime RenderContext 识别设备代次，在使用时重新创建和上传缓冲；不逐帧使用 isBuffer/isProgram 检测句柄。OpenGL 位图缓存的缓存渲染器属于旧设备时，缓存失效并从源显示对象重新绘制。

hxmaker-openfl Engine 监听 Window 的上下文丢失与恢复事件。丢失时暂停渲染帧入口；恢复事件只增加代次并标记待处理。等 OpenFL 新 Context3D 就绪后，在正常帧入口统一执行：

1. 保留当前字形缓存对象及字体、尺寸配置，丢弃失效字形，让全部驻留文字重新排队生成。
2. 清除失效的舞台位图池目标，保留池配置，下次使用时创建新目标。
3. 让主渲染器的批次数据和位图缓存失效，并递归标记舞台、显示对象、滤镜及 Scene3D 需要重绘。
4. MakerDisplay 与离屏 Render 按设备代次处理自身缓存；无需维护持有所有渲染器的全局强引用列表。
5. 恢复正常更新，并记录完成恢复次数。注册和卸载上下文事件均有明确入口。

普通 Assets 图片保留其 CPU 来源，沿用 OpenFL 按新 RenderContext 重新上传的机制，不清空 Assets、不重建业务场景。无法从源显示对象或资源重新生成的任意 GPU 图片，不通过伪造空白图冒充恢复成功。

## 首轮反馈后的文字修补

单纯标记文字过期并不足以证明 GPU 字形图集中已有有效像素。当前 HTML5 普通加载保持原 GPU 图集；首次恢复时，默认通过 Canvas 生成保留 CPU 像素的字形图集，纹理在新设备上重新上传。以后再次恢复可保留字形像素和坐标，文字布局仍重新准备；诊断按钮可强制清空并重建图集。

`TextFieldContextBitmapData.recoverWithCpuAtlas` 在 HTML5 默认 true，`cpuAtlasEnabled` 记录实际模式。额外 CPU 像素按 2048×2048 RGBA 每张约 16MiB 估算，浏览器可能还有其他副本。这部分成本只在恢复后的图集路径产生，不为普通初始帧新增 GPU 状态查询。

同时修复 BitmapData.draw 的缓存渲染器设备判断，以及 GPU 清屏时使用当前纹理。新增文字诊断区分“恢复事件到达”“后端入口完成”“文字完成预写”和“人工看到正确画面”，避免仅用 recovered 计数认定文字恢复成功。
