# 浏览器失焦缩放黑屏回归

日期：2026-11-06。结论：已复现并修复，上次版本把浏览器窗口失焦当成页面隐藏是本次回归原因。

## 故障路径

1. 页面正常显示，document.hidden=false。
2. DOM blur 经 Lime/OpenFL 转发为 DEACTIVATE，旧 Engine 将 applicationVisible 设为 false。
3. 调整窗口尺寸后画布清空，但帧入口和二维提交均因为该标志停止，尺寸重建请求无法消费。
4. focus 将标志恢复，下一帧才重新显示。

修复前记录中，失焦缩放后的更新数停在 40、提交数停在 30，resizePending=true；重新发送 focus 后恢复。这也说明之前先恢复前台再单独改变尺寸的验证没有覆盖事件交错。

## 修复

仅修改 hxmaker-openfl 的 Engine.hx：普通 HTML5 浏览器依据 Page Visibility 状态判断是否暂停；单纯失焦仍继续更新和处理尺寸重建。增加配对、幂等的 visibilitychange 监听，页面真正隐藏时暂停，恢复可见后请求一次重绘。Stage.onActivate/onDeactivate 的业务回调继续保留。

微信适配的 onHide/onShow 仍沿用激活事件语义；无可见性 API 的宿主也保持该兼容路径。没有修改 OpenFL、Lime 或生成的引擎 JS。

## 验证

- 旧版本成功复现清空画面，focus 后恢复。
- 修复后可见页面收到 blur，再改变尺寸，更新数增长到 55、提交数增长到 47，重建请求已消费。
- 连续 40 次失焦缩放，不发送 focus 或鼠标事件，画面恢复且持续更新。
- 真正隐藏的状态注入仍暂停；仅恢复 visible、不发送 focus，更新和实际绘制均恢复。
- 6 项专项像素检查通过：修复前清空、修复后有内容、恢复原尺寸和恢复 visible 后与初始画面逐像素一致。
- 原压力矩阵重跑通过：200 轮资源切换、100 次前后台模拟、90 次失焦尺寸变化、20 次设备恢复、ASTC→PNG 回退及 31 项原像素检查。正常流程错误为 0，受检纹理持有数保持 16。
- 浏览器和微信 JS 示例均编译通过。未重跑此前的性能及 1000 轮内存测试；这些记录保留原有指纹，本次修改不在逐帧纹理提交热路径中。

Headless Chrome 未在独立窗口切换时产生原生 blur，因此专项通过 DOM blur 重放现有 Lime/OpenFL 事件转发；页面可见性测试使用状态注入。没有将这两项冒充原生系统拖动窗口或微信真机操作，用户仍可按最初的真实操作复测。
