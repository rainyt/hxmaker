# OpenFL 二维渲染性能评估与基线方案

评估日期：2026-10-24。

后续已按用户要求完成默认直接渲染升级与基线实测，见 [性能实测报告](OpenFL二维渲染性能实测.md)。以下内容保留为实施前的评估记录。

本轮只做源码分析和方案设计，没有编译、运行示例或执行性能测试；下述收益均为待验证的判断，没有实测加速比例。

## 结论

可以跳过 OpenFL Graphics API，同时保留 OpenFL 的窗口、输入、资源和显示树集成。建议在 `hxmaker-openfl` 中增加可切换的二维直接提交路径，通过 `RenderEvent.RENDER_OPENGL` 接入，使用持久 CPU 类型化数组、GPU 顶点缓冲和索引缓冲提交批次。

优先优化普通 Image、Quad 以及可兼容的图集文字批次。先保留原 Graphics 路径作为对照与兼容回退，再逐步接入颜色变换、任意三角形、遮罩及离屏绘制。首轮不建议重写整个引擎，也不建议直接把实例化渲染作为通用替代。

当前代码确有可消除的重复遍历与复制，但不能仅凭源码认定数组分配就是主要瓶颈。实际收益取决于显示树更新、数据整理、GPU 上传、状态切换和像素填充分别占多少时间。

## 当前数据路径与可见开销

```text
hxmaker 显示树及世界变换
  → ImageBufferData：写入坐标、UV、索引、透明度、纹理编号等
  → Render.renderImageBuffData：设置 ShaderParameter.value
  → Graphics.beginShaderFill：ShaderBuffer.update 复制参数快照
  → Graphics.drawTriangles：遍历坐标计算边界并记录命令
  → OpenFL 实际绘制：Context3DGraphics 再整理顶点及索引
  → 上传几何缓冲、Shader 属性缓冲
  → GPU 绘制
```

### 1. 合批已经存在，仍逐帧重写数据

后端 `src/hx/render/ImageBufferData.hx:336` 的 `draw()` 已支持多纹理合批；但坐标、UV、索引及逐顶点属性仍逐次写入。用于跳过变换或 UV 更新的脏检测代码目前主要处于注释状态。

普通图片无颜色变换时，每个对象在这一层写入 28 个浮点值及 6 个索引：8 个坐标、8 个 UV、4 个纹理编号、4 个透明度及 4 个 ADD 标记。启用颜色变换时还增加 36 个浮点值。这是源码中的写入数量，不是实际分配量或最终 GPU 上传字节数。

`reset()` 保留了多数数组；`endFill()` 调整有效长度。应区分“每帧重写”“容量扩展”“类型转换”和“新建对象”。不能把所有 `resize` 都认定为重新分配。

### 2. Shader 参数确实存在中间复制

后端 `src/hx/core/Render.hx:197` 设置 `ShaderParameter.value`，然后执行 `beginShaderFill` 和 `drawTriangles`。

当前 OpenFL 的 `src/openfl/display/_internal/ShaderBuffer.hx:113` 中，`update()` 会把参数逐元素写入内部 `Float32Array`。容量不足时才扩容，但参数复制仍然发生。

当前 OpenFL 的 `src/openfl/display/Shader.hx:791` 中，`__updateGLFromBuffer()` 使用 `bufferData(..., DYNAMIC_DRAW)` 提交参数缓冲。不能简单断言把它改为 `bufferSubData` 就一定更快：覆盖 GPU 仍在读取的存储也可能产生等待，需要对照测量。

### 3. Graphics 增加了边界扫描和几何整理

当前 OpenFL 的 `src/openfl/display/Graphics.hx:1063` 会扫描所有顶点计算边界。

`src/openfl/display/_internal/Context3DGraphics.hx:240` 随后把坐标、UV 和索引写入自己的缓冲，再上传 GPU。直接提交路径可以去掉这次通用命令解释和数据重组。

需要避免一个误判：当前本地 OpenFL 已包含 `useDrawElements` 条件分支。不能假设现有路径一定把四边形的 4 个顶点展开成 6 个顶点，也不能把“改用索引绘制”直接当成新增收益。后续需记录实际执行的绘制分支和上传量。

### 4. 还有少量分配及显示树维护成本

`Render.renderImageBuffData()` 每批创建局部数组、映射及舞台尺寸数组，其中有当前方法内没有实际消费的局部变量。`clear()` 每次重建绘制树并收集待归还对象，虽然 Sprite 已池化，仍有拆离、添加、清理和临时数组的成本。

这些可以低成本整理，但单独去掉几个小数组，通常不足以消除随对象数增长的数据整理成本。收益大小待测。

### 5. 现有 CPU 指标覆盖不完整

后端 `src/hx/core/Engine.hx:421` 在更新及构造渲染命令后调用 `ContextStats.statsCpu()`；OpenFL 随后的实际绘制不在这个完整计时范围内。

新增的直接提交也会在 OpenFL 回调中执行。若只对比 `ContextStats.cpu` 或 `frameUsedTime`，可能把工作移动到计时区间之外误判成性能提升。基线需要额外覆盖 OpenFL 实际渲染阶段，并单独记录帧间隔。

## 可选优化路线

| 路线 | 能减少的开销 | 局限 | 建议 |
| --- | --- | --- | --- |
| 保留 Graphics，整理临时分配、缓存 UV 和索引 | 少量分配及重复计算 | 仍有 ShaderBuffer 复制和 Graphics 重组 | 作为独立对照组 |
| 绕过 Graphics，直接调用 Context3D 缓冲与绘制接口 | Graphics 命令、边界扫描及重组 | 自定义属性和 OpenFL 状态协议仍需适配 | 可作为兼容性较强的实现备选 |
| 在 RENDER_OPENGL 中直接提交 GL 缓冲 | 可控制数据布局、复制、上传和资源生命周期 | 需维护共享 GL 状态及版本适配 | 推荐主方案 |
| Tilemap | 适合图片或图块类对象 | 需要适配现有多纹理、任意网格和绘制顺序 | 特定场景备选 |
| 实例化四边形 | 减少每个图片重复的顶点属性和 CPU 展开 | 需要 WebGL 2 或扩展；任意网格不适用 | 直接提交稳定后再评估 |
| 完全独立 Lime/GL 后端 | 最大控制权 | 重写资源、文字、合成等集成成本高 | 当前不优先 |

OpenFL 官方提供 [RenderEvent](https://api.openfl.org/openfl/events/RenderEvent.html) 和 [OpenGLRenderer](https://github.com/openfl/openfl/blob/develop/src/openfl/display/OpenGLRenderer.hx) 接入方式，但将它们标为 Beta，需锁定并验证实际使用的版本。官方也提供 [VertexBuffer3D.uploadFromTypedArray](https://api.openfl.org/openfl/display3D/VertexBuffer3D.html) 和面向图块的 [Tilemap](https://api.openfl.org/openfl/display/Tilemap.html)。

## 推荐的直接提交设计

现有后端 `Scene3DDisplay` 已通过 `RENDER_OPENGL` 将自定义绘制嵌入 OpenFL 显示顺序；`MainGeometryBuffer3D` 已有类型化数组、容量增长和持久 GPU 缓冲；`TextureBridge3D`、`RenderStateGuard3D` 提供纹理与状态管理参考。

二维实现可以借鉴这些机制，但不直接套用完整三维渲染器。三维路径含离屏目标、合成及较多状态保存，对二维每个小批次照搬可能抵消收益。

建议分两步实现：

1. 保持现有显示树遍历及批次划分，只替换批次提交，先测出绕过 Graphics 的独立收益。
2. 再让批次生产器直接写入持久类型化数组，减少普通数组到类型化数组的搬运。保持容量与有效长度分离，按倍数扩容。

缓冲策略：

- 普通图片使用固定四边形索引，只在容量增长时生成及上传索引。
- 通用 Graphics、Spine 等网格单独处理动态拓扑，不能套用固定索引缓存。
- 起步可使用交错顶点布局；UV、颜色等冷热属性拆分需根据实际变化频率再测，避免先增加绑定成本。
- 静态批次在内容未变时不重新上传；缓存键必须覆盖对象顺序、可见性、变换、纹理及图集版本、透明度、颜色、混合模式和裁剪等。
- 对全量移动场景对比 `bufferSubData`、流式重新指定存储或轮换缓冲，不能预设某种策略在所有设备最快。
- WebGL 1 的 16 位索引路径按顶点数拆批；建议每批最多 16,383 个独立四边形。超过上限时不得产生索引溢出。
- 保持透明对象的原始绘制顺序，不能为减少纹理切换任意排序。

集成边界：

- 在对应批次显示节点的渲染回调中提交，不能统一拖到帧末，避免破坏二维、三维及原生对象的前后关系。
- 共享 OpenFL 纹理，处理纹理更新、释放和上下文恢复，不复制整套资源系统。
- 使用回调所对应的变换、目标 framebuffer、viewport、像素比和裁剪状态；不能只按主舞台尺寸推算。
- 保持预乘透明度与当前 NORMAL/ADD 合批语义。颜色变换、抗锯齿覆盖率也需保持一致。
- 先让自定义 Shader、滤镜、位图缓存及未适配的裁剪组合走原路径；涉及祖先合成状态时，按完整受影响子树回退，不能只替换单个叶节点。
- 已入队的批次在 OpenFL 消费前不能重置或覆写；同帧多舞台、离屏和重复渲染也必须隔离数据生命周期。
- 不在每个小批次中执行大批同步 GL 状态查询。优先沿用状态缓存或统一的进入、恢复协议，并测量边界开销。
- Canvas、Cairo 等非 GL 渲染保留现有路径；原生平台和小游戏平台逐一验证后再启用。

## 大量对象基线示例设计

建议放在 `samples/render-benchmark/`，入口 `Main` 继承 `hx.core.HxmakerApplication`，构造函数先 `super()`，再 `init(GameStage, width, height)`。场景和采样放在业务舞台及独立辅助类中。

现有后端 `WabbitRender` 可以借鉴，但它使用随机初始化、交互式加对象和运动逻辑，没有自动化的固定负载、重复采样与结果导出，不能直接作为可复现的正式基线。

### 对照组

| 组别 | 实现 | 用途 |
| --- | --- | --- |
| A | 当前 Graphics 路径原样保留 | 基线 |
| B | Graphics 路径，仅整理临时分配和明确重复计算 | 分离低成本优化收益 |
| C | 保持 A 的批次生产，替换直接提交 | 分离提交路径收益 |
| D | 直接提交并直接写类型化数组、缓存固定索引 | 测完整数据路径收益 |

每组保持相同纹理数、对象状态、混合语义、分辨率和更新逻辑；记录批次数差异的原因。实例化路径后续作为独立组加入，避免把不同优化混成一个结论。

### 工作负载

- 对象数：1,000、5,000、10,000、20,000、50,000；设备允许时追加 100,000，并设置长帧停止条件。
- 单纹理图片全量移动：放大变换、顶点生成及提交成本。
- 多纹理图片全量移动：使用固定纹理序列；补充超出纹理槽数量的场景检查拆批。
- 静止场景：分别测自然静止复用和强制重建批次，防止只测到引擎的脏帧跳过。
- 局部变化场景：固定比例对象移动，判断脏缓存是否值得实现。
- 补充场景：透明度、NORMAL/ADD、颜色变换、图集文字、遮罩、滤镜和任意网格。它们用于功能与代表性验证，不混入基础图片场景解释收益。
- 绘制小对象的低覆盖场景，并单独补充高重叠透明场景，区分 CPU 开销和 GPU 填充限制。

固定随机种子、模拟步长、逻辑尺寸及实际渲染像素尺寸。纹理在测量前生成或加载完成；排除首次 Shader 编译和首次纹理上传。计时期间不逐帧更新 Label、打印日志或拼装结果 JSON。

### 采样与结果

初始协议建议每场景预热 5 秒、采样 15 秒、至少重复 5 次，并交替执行对照组。全部使用相同发布配置、浏览器、设备和依赖快照；记录 GPU、WebGL 版本、窗口大小、DPR、前后台状态及可用扩展。首次加载成本另外记录。

逐帧采样写入预分配缓冲，结束后统一汇总并导出 JSON/CSV：

- 帧间隔的 P50、P95、P99、平均值及超预算帧比例。
- 更新、显示树遍历、批次生产、命令提交、OpenFL 实际渲染的 CPU 耗时；区间说明是否包含子区间，禁止重叠相加。
- 实际 GL drawArrays/drawElements 次数、上传调用次数、上传字节数、缓冲扩容次数、回退批次数。
- JS 堆内存趋势；分配和 GC 使用独立分析轮次，工具不支持时明确标记不可用，不能用堆差值代替分配量。
- GPU 时间仅在计时扩展可用时异步读取并排除 disjoint 样本；没有扩展时标记不可用，不能拿 JS 提交耗时当 GPU 时间。
- 正确性通过单独的截图或像素对照验证，避免读回污染性能采样。

实际 GL 计数插桩和浏览器性能录制应有独立诊断轮次，正式计时尽量减小插桩影响。不使用逐帧 `gl.finish()` 强制同步。60 FPS 封顶时优先比较耗时和长帧，而不是只看 FPS。

改进比例按相同负载下的耗时计算：`(基线耗时 - 优化耗时) / 基线耗时`；同时保留绝对毫秒数、重复轮次分布及原始数据，不能只报告最好的一轮。

## 实施顺序与本轮状态

1. 固定当前核心、后端及 OpenFL 的代码快照，建立可复现的基线示例和完整计时边界。
2. 增加可切换的直接提交原型，先覆盖单纹理、多纹理普通图片及原始绘制顺序。
3. 在执行编译验证、正确性检查及性能测试前先通知用户；本轮不执行这些操作。
4. 完成真实设备对照后，依据各阶段耗时决定继续做类型化数组直写、增量上传、静态缓存还是实例化。
5. 覆盖混合、裁剪、文字、滤镜、上下文恢复及目标平台后，再考虑调整默认路径。

本轮仅新增此评估文档，尚未创建基线示例或修改生产渲染路径。现阶段可以确认技术路线可行，不能确认加速幅度。
